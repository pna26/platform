    Observabilidade

    Responsável: Gabriel

    Problema

    Com várias réplicas do gateway atrás do Nginx, um cache no Redis e um serviço que depende de uma API externa, não dava para saber o que estava acontecendo sob carga: qual réplica recebe mais requisições, se o cache está acertando, se os erros vêm do gateway ou do Exchange, se a JVM está perto do limite de memória. Sem isso, o teste de carga só mostraria o número final do cliente, sem explicar o porquê.

    Solução

    Prometheus raspa as métricas de cada réplica a cada 5 s e o Grafana mostra um dashboard versionado no repositório, provisionado automaticamente (sem clicar na interface).

    flowchart LR
    subgraph trusted [Rede interna]
        gw1["gateway 1"] & gw2["gateway 2"] -.->|"/gateway/actuator/prometheus"| prom[(Prometheus)]
        ex["exchange"] -.->|"/metrics"| prom
        prom --> graf[Grafana]
    end
    k6([k6]) -->|remote write| prom
    dev([você]) -->|"127.0.0.1:3000"| graf
    Decisão Motivo
    dns_sd_configs no compose O nome gateway resolve para todos os IPs das réplicas; cada uma vira um alvo (instance). Com static_configs cada scrape cairia numa réplica aleatória e as séries se misturariam. --scale gateway=N entra sozinho em até 10 s.
    kubernetes_sd_configs + anotações prometheus.io/* no EKS O Prometheus descobre os pods do namespace; quem quer ser raspado só anota o pod (gateway e exchange já anotam). RBAC com Role só de leitura no namespace, não ClusterRole.
    Métricas fora da internet O lb responde 404 para /gateway/actuator/** e o gateway só encaminha /exchange/** (o /metrics do exchange fica de fora). Prometheus e Grafana: 127.0.0.1 no compose e ClusterIP + port-forward no EKS.
    Dashboard em JSON no git (setup/grafana/dashboards/store.json) O mesmo arquivo serve o compose (volume) e o EKS (ConfigMap criado pelo workflow infra). Mudou o dashboard → PR.
    Remote write do k6 O teste de carga aparece no mesmo dashboard, no mesmo eixo de tempo das métricas do servidor.
    Senha do Grafana fora do git Compose: GRAFANA_ADMIN_PASSWORD no .env. EKS: Secret criado pelo workflow (secret da org ou aleatória).
    Exchange com histograma; gateway com média/máximo O exchange publica buckets (exchange_http_server_requests_seconds_bucket), então tem p50/p95/p99. O Spring Boot não publica buckets por padrão; os percentis do lado do cliente vêm do k6.

    Métricas usadas

    Origem Métrica Para quê
    gateway (Micrometer) http_server_requests_seconds_{count,sum,max} req/s por status e por réplica, latência média/máxima, taxa de 5xx
    gateway gateway_token_cache_total{result} acerto do cache do token
    gateway jvm_memory_used_bytes, process_cpu_usage memória e CPU por réplica
    exchange exchange_http_server_requests_seconds (histograma, label route = template) req/s e p50/p95/p99 da cotação
    exchange exchange_quote_cache_total{result} acerto do cache da cotação
    exchange exchange_upstream_request_seconds{outcome} chamadas e latência da API externa
    Prometheus up{job} réplicas no ar
    k6 k6_vus, k6_http_reqs_total, k6_http_req_duration_p95/p99 carga aplicada e latência vista pelo cliente

    O label route do exchange usa o template da rota (/exchange/{from_}/{to}), não a URL real: senão cada par de moedas criaria uma série nova no Prometheus (explosão de cardinalidade). Há um teste para isso.

    Dashboard

    Store — plataforma (pasta Store, também é a página inicial do Grafana):

    Linha Painéis
    Visão geral req/s, % de 5xx (verde/laranja/vermelho), réplicas no ar por serviço, % de acerto do cache do token
    Gateway req/s por status, latência média/máxima, req/s por réplica (mostra o balanceamento), cache hit/miss/error, heap e CPU por réplica
    Exchange cotações/s por status, p50/p95/p99, cache da cotação × chamadas à API externa
    Teste de carga (k6) VUs e req/s, p95/p99 do cliente por cenário

    Como usar

    docker compose up -d --build
# Grafana:    http://localhost:3000   (admin / GRAFANA_ADMIN_PASSWORD do .env)
# Prometheus: http://localhost:9090/targets   (uma linha por réplica)

    kubectl port-forward svc/grafana 3000 -n store
kubectl get secret grafana-admin -n store -o jsonpath='{.data.password}' | base64 -d
kubectl port-forward svc/prometheus 9090 -n store

    Para ver o dashboard se mexer, rode um teste de carga em outro terminal.

    Resultado: o que a observabilidade mostrou

    Verificado em 05/11/2026 com a plataforma local no ar: o Prometheus descobriu sozinho as 2 réplicas do gateway e o exchange (/targets, todos up), o Grafana subiu com o data source e o dashboard já provisionados, e todas as consultas do dashboard retornam dados.

    Durante o teste de carga foi a observabilidade que explicou os números que o k6 só mostrava de fora:

    Pergunta Onde a resposta apareceu
    O cache do token está mesmo poupando o Auth? gateway_token_cache_total: 7.571 hits × 21 misses na rodada com cache (99,7 %).
    Por que 4 réplicas renderam menos que 1 na saturação? CPU da máquina (system_cpu_usage) em ≈ 83–85 % nas duas rodadas: as réplicas disputavam os mesmos núcleos.
    De onde vieram os 0,57 % de erro na saturação? http_server_requests_seconds_count{status="500"} no gateway (≈ 3.500) → logs do Auth: BindException ao chamar o Account (Feign sem pool de conexões).

    Sugestão para o gateway (Leonardo)

    Ligar spring.cloud.gateway.server.webflux.metrics.enabled=true no gateway publicaria spring_cloud_gateway_requests_seconds com o routeId, o que permitiria quebrar a latência por rota (auth × account × exchange). Também management.metrics.distribution.percentiles-histogram.http.server.requests=true daria p95/p99 do lado do servidor.

    Configuração

    # Bottleneck: observabilidade. Prometheus do compose local.
#
# O gateway e o exchange têm várias réplicas atrás do mesmo nome DNS. Com
# static_configs ("gateway:8080") cada scrape cairia numa réplica aleatória e as
# séries se misturariam; com dns_sd_configs o Prometheus resolve o nome para
# TODOS os IPs e raspa cada réplica separada (label "instance" = IP da réplica).
# "--scale gateway=N" entra sozinho em até 10 s.

global:
  scrape_interval: 5s
  evaluation_interval: 15s

scrape_configs:

  - job_name: gateway
    metrics_path: /gateway/actuator/prometheus
    dns_sd_configs:
      - names: [ gateway ]
        type: A
        port: 8080
        refresh_interval: 10s

  - job_name: exchange
    metrics_path: /metrics
    dns_sd_configs:
      - names: [ exchange ]
        type: A
        port: 8080
        refresh_interval: 10s

  - job_name: prometheus
    static_configs:
      - targets: [ localhost:9090 ]

    # Bottleneck: observabilidade no EKS. O Prometheus descobre os pods do próprio
# namespace pela API do Kubernetes e raspa os que têm as anotações
#   prometheus.io/scrape: "true", prometheus.io/path, prometheus.io/port
# (gateway-service/k8s e exchange-service/k8s já trazem). Cada réplica vira um
# alvo separado. Acesso: kubectl port-forward svc/prometheus 9090 -n store
apiVersion: v1
kind: ServiceAccount
metadata:
  name: prometheus
---
# só leitura de pods/endpoints do namespace (Role, não ClusterRole)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: prometheus
rules:
  - apiGroups: [ "" ]
    resources: [ pods, services, endpoints ]
    verbs: [ get, list, watch ]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: prometheus
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: prometheus
subjects:
  - kind: ServiceAccount
    name: prometheus
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-configmap
data:
  prometheus.yml: |
    global:
      scrape_interval: 15s
    scrape_configs:
      - job_name: pods
        kubernetes_sd_configs:
          - role: pod
            namespaces:
              own_namespace: true
        relabel_configs:
          - source_labels: [ __meta_kubernetes_pod_annotation_prometheus_io_scrape ]
            action: keep
            regex: "true"
          - source_labels: [ __meta_kubernetes_pod_annotation_prometheus_io_path ]
            action: replace
            target_label: __metrics_path__
            regex: (.+)
          - source_labels: [ __address__, __meta_kubernetes_pod_annotation_prometheus_io_port ]
            action: replace
            regex: ([^:]+)(?::\d+)?;(\d+)
            replacement: $1:$2
            target_label: __address__
          # job = label "app" do pod (gateway, exchange...), como no compose
          - source_labels: [ __meta_kubernetes_pod_label_app ]
            target_label: job
          - source_labels: [ __meta_kubernetes_pod_name ]
            target_label: pod
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: prometheus
  labels:
    app: prometheus
spec:
  replicas: 1
  selector:
    matchLabels:
      app: prometheus
  template:
    metadata:
      labels:
        app: prometheus
    spec:
      serviceAccountName: prometheus
      securityContext:
        runAsNonRoot: true
        runAsUser: 65534
        runAsGroup: 65534
        fsGroup: 65534
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: prometheus
          image: prom/prometheus:v3.5.0
          args:
            - --config.file=/etc/prometheus/prometheus.yml
            - --storage.tsdb.path=/prometheus
            # sem volume persistente: guarda só o suficiente para os testes/demonstração
            - --storage.tsdb.retention.time=2d
            - --web.enable-remote-write-receiver
          ports:
            - containerPort: 9090
          readinessProbe:
            httpGet:
              path: /-/ready
              port: 9090
            periodSeconds: 10
          resources:
            requests:
              memory: "256Mi"
              cpu: "100m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: [ "ALL" ]
          volumeMounts:
            - name: config
              mountPath: /etc/prometheus
            - name: data
              mountPath: /prometheus
      volumes:
        - name: config
          configMap:
            name: prometheus-configmap
        - name: data
          emptyDir: {}
---
apiVersion: v1
kind: Service
metadata:
  name: prometheus
spec:
  type: ClusterIP
  selector:
    app: prometheus
  ports:
    - protocol: TCP
      port: 9090
      targetPort: 9090

    # Bottleneck: observabilidade no EKS. Grafana sem porta pública (ClusterIP):
#   kubectl port-forward svc/grafana 3000 -n store   ->  http://localhost:3000
# O ConfigMap "grafana-dashboards" (setup/grafana/dashboards/*.json) e o Secret
# "grafana-admin" são criados pelo workflow infra (assim o JSON do dashboard
# não fica duplicado e a senha não fica no git).
apiVersion: v1
kind: ConfigMap
metadata:
  name: grafana-provisioning
data:
  datasources.yaml: |
    apiVersion: 1
    datasources:
      - name: Prometheus
        uid: prometheus
        type: prometheus
        access: proxy
        url: http://prometheus:9090
        isDefault: true
  dashboards.yaml: |
    apiVersion: 1
    providers:
      - name: store
        folder: Store
        type: file
        allowUiUpdates: false
        options:
          path: /var/lib/grafana/dashboards
---
