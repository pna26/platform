    Mensageria (Kafka)

    Responsável: Nicolas

    Segue o Hands-on 7 — Mensageria assíncrona do curso (Kafka no compose, transactional outbox, consumidor idempotente e DLT), adaptado da venda de ingressos do BoxOffice para o cadastro de contas da loja.

    Problema

    Depois de criar uma conta, a loja quer mandar um e-mail de boas-vindas. Se o account chamasse o serviço de e-mail dentro do POST /accounts, o cadastro ficaria acoplado a ele:

    • o usuário esperaria a latência do provedor de e-mail (dezenas a centenas de ms por envio);
    • uma queda do e-mail viraria uma queda do cadastro;
    • um pico de cadastros bateria no provedor de e-mail na mesma hora, no mesmo ritmo.

    O trabalho que o usuário não precisa esperar sai do caminho da requisição e vai para um broker.

    Solução

    flowchart LR
    u([Usuário]) -->|"POST /auth/register"| auth --> account
    subgraph tx ["uma transação no PostgreSQL"]
        account -->|"INSERT"| acc[("accounts.accounts")]
        account -->|"INSERT AccountCreated"| ob[("accounts.outbox")]
    end
    relay["OutboxRelay<br/>(a cada 200 ms)"] -->|"lê pendentes"| ob
    relay -->|"chave = id da conta<br/>acks=all"| k[["Kafka<br/>account-events (6 partições)"]]
    k -->|"grupo notification"| n["notification-service"]
    n -->|"dedupe por eventId"| pe[("notification.processed_events")]
    n -->|SMTP| mail(["Mailpit"])
    n -. "falha permanente" .-> dlt[["account-events-dlt"]]
    dlt --> dl[("notification.dead_letters")]

    A requisição do usuário termina no commit do banco. Publicar, enviar o e-mail e tentar de novo acontece depois, de forma assíncrona, e pode ser lento, falhar ou se repetir sem que o usuário perceba.

    Decisão Motivo
    Kafka (4.3, um nó em modo KRaft) É o broker do material do curso (Hands-on 7). O log é retido depois do consumo: dá para reprocessar e um consumidor novo pode ler o histórico.
    Transactional outbox no account Gravar a conta e depois publicar no Kafka são duas escritas em sistemas diferentes: se o processo cair entre elas, perde-se o evento (ou publica-se um evento de uma conta que não existe). Com o outbox, a conta e o evento entram na mesma transação; um relay publica depois do commit. E-mail duplicado (rollback) não deixa evento órfão.
    Relay com FOR UPDATE SKIP LOCKED Várias réplicas do account podem rodar o relay sem publicar a mesma linha duas vezes ao mesmo tempo.
    Produtor com acks=all e enable.idempotence O broker só confirma depois de gravar; um reenvio do produtor não duplica a mensagem no log.
    Chave da mensagem = id da conta Eventos da mesma conta caem na mesma partição: o Kafka só garante ordem dentro da partição.
    6 partições, criadas pelo kafka-init O número de partições é o teto de consumidores paralelos do grupo. A criação automática está desligada (daria 1 partição).
    Consumidor idempotente A entrega é at-least-once: o mesmo evento pode chegar duas vezes (consumidor caiu depois de enviar e antes do commit do offset, ou reprocessamento). O eventId é gravado em processed_events na mesma transação do registro do e-mail; se já existe, o evento é ignorado.
    3 retries com backoff (0,5 s, 1 s, 2 s) e DLT Falha temporária (SMTP fora) é tentada de novo; depois disso a mensagem vai para account-events-dlt e a partição continua andando. JSON inválido ou evento sem campos obrigatórios vão direto para a DLT: tentar de novo não adianta.
    O evento não leva senha nem hash Só eventId, eventType, accountId, name, email e occurredAt: o mínimo para o e-mail.
    Schema próprio (notification) O consumidor guarda o seu estado no mesmo PostgreSQL, sem tocar nas tabelas do account.
    Kafka sem porta publicada; Kafka UI e Mailpit só em 127.0.0.1 O broker não tem autenticação: fica na camada confiável (rede do compose / ClusterIP no k8s), como o Redis.

    @Transactional
    public Account create(Account account) {

        if (null == account.password()) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Password is empty"
            );
        }

        final String pass = account.password().trim();
        if (pass.length() < 6) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Password must have at least 6 characters"
            );
        }

        if (account.email() == null || account.email().trim().isEmpty()) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Email is empty"
            );
        }

        account.hashPassword(calcHash(pass));

        final Account saved = accountRepository.save(
            new AccountModel(account)
        ).to();

        final AccountEvent event = AccountEvent.created(saved);
        outbox.append(event.eventId(), "account", saved.id(), event.eventType(), event);

        return saved;
    }

    package store.account.outbox;

import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.List;
import java.util.UUID;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

import org.apache.kafka.clients.producer.ProducerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.SendResult;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

/** Publica no Kafka os eventos que o Outbox gravou, depois do commit (Hands-on 7). */
@Component
public class OutboxRelay {

    private static final Logger log = LoggerFactory.getLogger(OutboxRelay.class);

    record Pending(UUID id, String aggregateId, String eventType, String payload) {
    }

    private final JdbcClient jdbc;
    private final JdbcTemplate jdbcTemplate;
    private final KafkaTemplate<String, String> kafka;
    private final String topic;

    public OutboxRelay(JdbcClient jdbc, JdbcTemplate jdbcTemplate,
                       KafkaTemplate<String, String> kafka,
                       @Value("${store.account.topic}") String topic) {
        this.jdbc = jdbc;
        this.jdbcTemplate = jdbcTemplate;
        this.kafka = kafka;
        this.topic = topic;
    }

    @Scheduled(fixedDelayString = "${store.account.relay-interval-ms:200}")
    @Transactional
    public void relay() throws Exception {
        // SKIP LOCKED: várias réplicas do account podem rodar o relay sem pegar as mesmas linhas
        List<Pending> batch = jdbc.sql("""
                SELECT id, aggregate_id, event_type, payload::text AS payload
                FROM accounts.outbox
                WHERE published_at IS NULL
                ORDER BY created_at
                LIMIT 100
                FOR UPDATE SKIP LOCKED
                """)
                .query(Pending.class)
                .list();
        if (batch.isEmpty()) {
            return;
        }

        List<CompletableFuture<SendResult<String, String>>> acks = new ArrayList<>();
        for (Pending p : batch) {
            // chave = id da conta: eventos da mesma conta caem na mesma partição (ordem por chave)
            ProducerRecord<String, String> record =
                    new ProducerRecord<>(topic, p.aggregateId(), p.payload());
            record.headers().add("eventId", p.id().toString().getBytes(StandardCharsets.UTF_8));
            record.headers().add("eventType", p.eventType().getBytes(StandardCharsets.UTF_8));
            acks.add(kafka.send(record));
        }
        // espera o ack de todos; se falhar, a transação volta e as linhas são tentadas de novo
        CompletableFuture.allOf(acks.toArray(new CompletableFuture<?>[0])).get(10, TimeUnit.SECONDS);

        jdbcTemplate.batchUpdate("UPDATE accounts.outbox SET published_at = clock_timestamp() WHERE id = ?",
                batch.stream().map(p -> new Object[] {p.id()}).toList());
        log.info("relayed {} event(s) to {}", batch.size(), topic);
    }

    @Scheduled(cron = "0 0 * * * *")
    @Transactional
    public void purge() {
        int n = jdbcTemplate.update(
                "DELETE FROM accounts.outbox WHERE published_at < now() - interval '1 day'");
        log.info("purged {} published outbox row(s)", n);
    }
}

    package store.notification;

import java.time.OffsetDateTime;
import java.time.ZoneOffset;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class NotificationService {

    private static final Logger log = LoggerFactory.getLogger(NotificationService.class);

    private final JdbcClient jdbc;
    private final EmailSender email;
    private final NotificationProperties props;

    public NotificationService(JdbcClient jdbc, EmailSender email, NotificationProperties props) {
        this.jdbc = jdbc;
        this.email = email;
        this.props = props;
    }

    /**
     * Entrega at-least-once: o mesmo evento pode chegar duas vezes. O eventId é
     * gravado na mesma transação do registro do e-mail; se já existir, é duplicata.
     *
     * @return true se enviou o e-mail, false se o evento era duplicado
     */
    @Transactional
    public boolean handle(AccountEvent e) {
        if (props.idempotent()) {
            int fresh = jdbc.sql("INSERT INTO processed_events (event_id) VALUES (?) ON CONFLICT DO NOTHING")
                    .param(e.eventId())
                    .update();
            if (fresh == 0) {
                log.info("duplicate event {} for account {} ignored", e.eventId(), e.accountId());
                return false;
            }
        }
        email.welcome(e); // se lançar, a transação inteira volta (inclusive a linha de deduplicação)
        jdbc.sql("""
                INSERT INTO notifications (event_id, account_id, email, kind, occurred_at)
                VALUES (?, ?, ?, ?, ?)
                """)
                .params(e.eventId(), e.accountId(), e.email(), e.eventType(),
                        OffsetDateTime.ofInstant(e.occurredAt(), ZoneOffset.UTC))
                .update();
        log.info("welcome e-mail sent for account {}", e.accountId());
        return true;
    }
}

    package store.notification;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.listener.DeadLetterPublishingRecoverer;
import org.springframework.kafka.listener.DefaultErrorHandler;
import org.springframework.kafka.support.ExponentialBackOffWithMaxRetries;

import tools.jackson.core.JacksonException;

@Configuration
public class KafkaConfig {

    /** Usado pela fábrica de listeners do Spring Boot (um único bean CommonErrorHandler). */
    @Bean
    DefaultErrorHandler errorHandler(KafkaTemplate<String, String> template) {
        // depois das tentativas, publica em <tópico>-dlt, mesma partição, com a exceção nos headers
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template);

        ExponentialBackOffWithMaxRetries backOff = new ExponentialBackOffWithMaxRetries(3);
        backOff.setInitialInterval(500L);  // 0,5 s, 1 s, 2 s
        backOff.setMultiplier(2.0);
        backOff.setMaxInterval(5_000L);

        DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);
        // falhas permanentes: tentar de novo não adianta, vai direto para a DLT
        handler.addNotRetryableExceptions(JacksonException.class, IllegalArgumentException.class);
        return handler;
    }
}

    Resultados

    scripts/messaging-test.sh no compose local (08/11/2026), 20 cadastros por experimento, latência simulada do e-mail de 50 ms, 3 threads consumidoras:

    Experimento O que aconteceu
    1. Caminho feliz 20 cadastros, média de 16 ms por POST /auth/register; 20 e-mails de boas-vindas no Mailpit.
    2. notification parado O cadastro continuou respondendo (15 ms). O lag do grupo subiu para 20 mensagens, guardadas no Kafka. Ao religar, o backlog drenou em 9 s (incluindo subir a JVM) e chegaram os 20 e-mails.
    3. Kafka parado O cadastro continuou respondendo (15 ms): os 20 eventos ficaram no outbox. Com o Kafka de volta, o relay publicou tudo e chegaram os 20 e-mails, nenhum evento perdido.
    4. Reprocessamento (offsets do grupo voltados ao início) O tópico inteiro foi relido e nenhum e-mail novo foi enviado: todos os eventos já estavam em processed_events.
    5. Mensagem envenenada (texto que não é JSON) Foi para account-events-dlt sem retry (StreamReadException) e ficou em dead_letters. Os 20 cadastros seguintes geraram os 20 e-mails: a partição não travou.

    Também conferido: um segundo cadastro com o mesmo e-mail (500, comportamento do curso) não deixa linha no outbox, porque o rollback desfaz a conta e o evento juntos.

    Com o e-mail no caminho síncrono

    Com o envio dentro da requisição, cada cadastro somaria a latência do provedor (50 ms simulados aqui, e centenas de ms em provedores reais) e falharia junto com ele. Nos experimentos 2 e 3 o cadastro ficou no mesmo tempo com o consumidor ou o broker fora do ar: é o desacoplamento que o gargalo pede.

    No EKS

    Os manifestos ficam prontos para quando o cluster eks-store for recriado (ver EKS):

    • k8s/kafka.yaml: Deployment de 1 réplica (KRaft), Service kafka (ClusterIP) e o Job kafka-init que cria os tópicos. O workflow infra.yaml aplica a pasta k8s/ junto com os outros manifestos.
    • k8s/mailpit.yaml: SMTP falso; a caixa de entrada só por kubectl port-forward -n store svc/mailpit 8025:8025.
    • api/notification-service/k8s/k8s.yaml: o consumidor (sem Service: ninguém o chama). O ConfigMap do account ganhou KAFKA_BOOTSTRAP_SERVERS.
    • Secret notification-secrets (usuário e senha do RDS) criado à mão, uma vez por cluster, como o account-secrets. Nunca vai para o Git.

    Os containers foram testados localmente com as mesmas restrições dos manifestos (usuário sem root, capabilities removidas, raiz somente leitura no Mailpit e no notification). Ainda não rodaram no EKS: o cluster está apagado por custo.

    Limites conhecidos

    • Kafka sem disco persistente no EKS: o cluster não tem o driver EBS CSI, então os dados ficam num emptyDir. Se o pod do Kafka reiniciar, as mensagens ainda não consumidas se perdem. Em produção: PersistentVolume, 3 brokers com replication-factor 3 ou o Amazon MSK (Kafka gerenciado).
    • Um broker só (replication-factor 1): sem tolerância a falha do broker. Os eventos esperam no outbox enquanto ele está fora (experimento 3), mas o broker é ponto único de falha da mensageria.
    • Sem autenticação no Kafka (PLAINTEXT): aceitável só porque ele não é alcançável de fora da rede interna.
    • O lag do consumidor ainda não está no Prometheus/Grafana; hoje é visto pelo Kafka UI ou pela CLI.
