    Use of AI

    The assignment allows partial use of AI in the implementation, as long as it is documented: what was done with AI help, what was done by the group, and everyone must be able to explain and defend any part (including the AI-generated ones). This page is that record — each member fills in their own part.

    Group rule

    Nothing generated by AI goes in unless the owner has read, run and understood it. Before the presentation we do an internal walkthrough in which each member explains the others' parts.

    How it was used: based on the project board and the course material (hands-on 2, 3, 4, 7 and 8 and the bottlenecks page), I asked the AI to implement my tasks. The AI generated the code, ran the tests and the platform locally, and opened the repositories/PRs. What I reviewed and changed is recorded below.

    What I (Leonardo) did without AI:

    • Project organization: I created the project board (26/10/2026) with the 22 task cards: the split of work among the three members, the weight of each deliverable and the owner of each item.
    • Group scope: I defined what each member delivers (services, bottlenecks, parts of the infra and the documentation) and the shared tasks (local compose, internal walkthrough, presentation).
    • API contract: I wrote the "Contrato de API Gateway/Auth/Account" card, the basis of the Architecture page: Gateway, Auth, Account and Exchange routes, open routes, JWT claims and duration, cookie configuration and the open questions, each with an owner (login route in Account, /exchange × /exchanges, service names in compose/k8s, HTTPS on EKS).
    • Review of the code generated by the AI: gateway, CI/CD pipeline, compose.yaml, Nginx and k8s manifests.
    • Directing the work with the AI: I chose which tasks would be done and approved each external action: creation of the gateway-service and platform repositories, CI PRs on Nicolas's repositories (via fork, for him to review) and board updates.

    Where the AI got it wrong and it was fixed:

    • The first with/without cache benchmark was invalid: the TOKEN_CACHE_ENABLED variable was not being passed by compose to the gateway, so both runs used the cache. It was fixed and measured again; the honest conclusion is that locally the latency stays the same and the gain is taking load off Auth.
    • Trivy aborts when --ignorefile points to a file that does not exist: the pipeline now only uses .trivyignore when it exists (the Account/Auth repositories don't have one).
    • WebClient.Builder is no longer auto-configured in Spring Boot 4 without spring-boot-starter-webclient (the integration test caught this).

    What I (Nicolas) did without AI:

    • AWS by hand: I ran the commands and did the console clicks (budget, SSO, ECR, CI role), checking each result with the AI.
    • Project decisions: region us-east-2 and a US$ 20/month cost alert; RDS PostgreSQL for the database on EKS; nodes only in private subnets and RDS without public access; deleting the environment whenever it is not in use; in messaging, the welcome email as the use case, the consumer in a separate service and following the professor's material (Kafka) instead of the RabbitMQ in the initial plan; in RBAC, new accounts are always USER and ADMIN only via the database.
    • Review: I read and understood each change before it went to GitHub, and tested in compose and on the cluster.
    • Rules for the AI: no secrets in Git, on screen or in logs; commits without AI co-authorship; changes to another member's repository only through PRs, for the owner to review. I approved each external action.

    Where the AI got it wrong and it was fixed:

    • OIDC rejected in the first CI run (Not authorized to perform sts:AssumeRoleWithWebIdentity): the trust policy expected repo:pna26/*, but the repositories use GitHub's immutable subject (repo:pna26@<id>/...). Fixed and documented in AWS.
    • ECR names: the first repositories (gateway, auth...) did not match the names the pipeline uses (*-service). They were recreated with the right names and the old, empty ones deleted.
    • docker login to ECR failed on Windows: the token exceeds the size the Credential Manager accepts. Solved with docker-credential-ecr-login.
    • CI permissions on the cluster: AmazonEKSEditPolicy did not allow creating Prometheus's Role, and not even AmazonEKSAdminPolicy solved it, because Kubernetes' privilege-escalation check does not see the AWS policy. The fix was a RoleBinding to the admin role, only in the store namespace.
    • Fallback JWT key in Auth's application.yaml: removed during the security review, and now Auth does not start without JWT_SECRET_KEY.
    • It used saveAndFlush, which does not exist in account's CrudRepository: the build caught it and it became save (the transaction still guarantees that the account and the event are saved together).
    • The messaging script failed in Git Bash on Windows: /opt/kafka/... became C:/Program Files/Git/opt/.... Fixed with MSYS_NO_PATHCONV=1.
    • smoke-test.sh expected any user to be able to GET /accounts (200); with RBAC it became 403, and the script got the new checks. The first JwtService test did not compile (invalid escape in a regular expression), and the build caught it before the commit.

    What I (Gabriel) did without AI:

    • Directing the work: I requested the tasks, required one commit per task and approved each external action: creation of the pna26/exchange-service repository (public, like the others), the PR via fork, the board update and the installs with administrator permission.
    • Environment: GitHub CLI login, authorizing the Projects scope, enabling virtualization/WSL and rebooting so Docker would work.

    Where the AI got it wrong and it was fixed:

    • k6 smoke profile did not run any iteration: it ramped from 0 to 1 user within its own 20 s. Noticed on the first run; it became 1 fixed user.
    • The 60 requests from setup() were included in the statistics (sign-up/login of the test accounts), skewing short runs. Fixed with the phase=setup|test tag.
    • The replicas experiment did not find a breaking point: with the pause between actions, 400 users generate only ≈ 290 req/s. The saturation experiment (THINK=0) was created, and it found the real bottleneck in Auth.
    • The AI edited load-matrix.sh while it was running: bash reads the script incrementally and started executing the wrong parts, corrupting the exchange-cache-off run. Experiment 3 was run again.
    • Caught before the commit: head -n -1 (does not work on the group's macOS), 2 uvicorn workers (each Prometheus scrape would see a different process) and the wrong lb requests in the cost calculation.
    • The EKS extended support alert was missing (US$ 0.60/h): it came up while checking the prices.
