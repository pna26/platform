    Testes de carga

    Responsável: Gabriel

    Ferramenta: k6 (Grafana Labs), rodando em container — ninguém do grupo precisa instalar nada além do Docker. Escolhemos o k6 em vez do JMeter/Locust porque o teste é um arquivo JavaScript versionado no repositório, os limites de aceitação (thresholds) ficam no próprio script e ele envia as métricas direto para o Prometheus, então a carga aparece no mesmo dashboard do Grafana que as métricas do servidor.

    O que é testado

    flowchart LR
    k6([k6<br/>N usuários virtuais]) ==> lb[lb · Nginx] ==> gw["gateway<br/>(1, 2 ou 4 réplicas)"]
    gw <-->|token| redis[(Redis)]
    gw --> auth & account & exchange
    exchange -->|miss| api([AwesomeAPI])
    k6 -.->|remote write| prom[(Prometheus)] --> graf[Grafana]

    O setup() do script cria 20 contas e faz login uma vez; depois os usuários virtuais (VUs) reaproveitam os tokens, como usuários reais navegando logados. Cada VU espera 0,5–1,5 s entre as ações.

    Cenário Requisições O que exercita
    auth GET /auth/me + GET /accounts/{id} validação do token (Redis ou Auth), balanceamento, Account + PostgreSQL
    exchange GET /exchange/USD/BRL (80 %) e EUR/BRL gateway → Exchange → cache da cotação / API externa
    login POST /auth/login caminho caro: hash da senha + emissão do JWT
    mixed 80 % leitura autenticada, 15 % câmbio, 5 % login uso "real" da loja
    Perfil Forma da carga Pergunta que responde
    smoke 1 VU, 20 s O script e a plataforma funcionam?
    load sobe em 20 s até VUS, mantém por DURATION, desce Aguenta a carga esperada dentro do SLO?
    stress VUS → ×2 → ×4 → ×8, 30 s cada Onde quebra? Qual componente satura primeiro?
    spike VUS/10 → pico de VUS×4 em 5 s → volta Aguenta um pico repentino e se recupera?

    Critérios de aceitação (os mesmos do SLO), checados pelo k6 — ele sai com código 99 se algum estourar:

    Métrica Limite
    Erros (http_req_failed) < 1 %
    Latência p95 / p99 (respostas esperadas) < 500 ms / < 1500 ms
    checks (status e conteúdo das respostas) > 99 %

    Como rodar

    ./scripts/build.sh && docker compose up -d --build     # plataforma + Prometheus + Grafana

./scripts/load-test.sh                                  # mixed, perfil load, 50 VUs, 1 min
SCENARIO=auth PROFILE=stress VUS=50 ./scripts/load-test.sh
SCENARIO=exchange PROFILE=spike VUS=20 ./scripts/load-test.sh
THINK=0 SCENARIO=auth PROFILE=stress VUS=25 ./scripts/load-test.sh   # sem pausa: limite de vazão
BASE_URL=http://<endereço-do-elb> ./scripts/load-test.sh   # contra o EKS

./scripts/load-matrix.sh        # todos os experimentos abaixo (~25 min) -> load/results/RESULTS.md

    Enquanto roda, abra o Grafana em http://localhost:3000: a linha Teste de carga (k6) mostra VUs, req/s e p95/p99 do cliente, e as linhas de cima mostram o que acontece em cada réplica, no Redis e no Exchange no mesmo instante.

    Experimentos

    O scripts/load-matrix.sh muda uma variável por vez e mantém o resto igual (cache do Redis esvaziado antes de cada rodada):

    # Experimento Variável Cenário / perfil Hipótese
    1 Cache do token TOKEN_CACHE_ENABLED = false × true auth / load Sem cache, cada requisição chama o Auth: mais carga no Auth e latência maior quando ele satura. Com cache, gateway_token_cache_total{result="miss"} fica perto de 20 (um por usuário).
    2 Réplicas do gateway GATEWAY_REPLICAS = 1 × 2 × 4 auth / stress Mais réplicas atrasam o ponto em que o p95 estoura — até o gargalo passar para outro componente (Account/PostgreSQL ou a própria CPU da máquina).
    3 Cache da cotação EXCHANGE_CACHE_TTL = 0 × 30 exchange / load, 10 VUs, 30 s Sem cache, a latência do Exchange é a da API externa e aparecem 429; com cache, ~1 chamada externa a cada 30 s por réplica. Poucos VUs de propósito: não queremos martelar um serviço de terceiros.
    4 Uso real configuração padrão mixed / load Dentro do SLO.
    5 Saturação GATEWAY_REPLICAS = 1 × 4, THINK=0 (sem pausa) auth / stress até 200 VUs Com pausa, o experimento 2 não chega ao limite; sem pausa, cada VU dispara o mais rápido possível e mostra o que quebra primeiro.

    Resultados

    Medidos em 05/11/2026 com ./scripts/load-matrix.sh (os experimentos 3 e 5 foram rodados de novo com ONLY="3 5"). Máquina: Windows 11 + Docker Desktop (WSL2), 12 CPUs lógicas, 7,3 GiB de RAM para o Docker. k6, Nginx, gateway, serviços, banco, Prometheus e Grafana na mesma máquina. Latências só das respostas esperadas e só da fase de teste (o cadastro/login do setup() fica de fora).

    Execução Cenário Perfil VUs máx. Requisições req/s p50 (ms) p95 (ms) p99 (ms) Erros
    token-cache-off auth load 50 7.416 80,8 5 12 20 0,00 %
    token-cache-on auth load 50 7.448 79,7 4 7 15 0,00 %
    replicas-1 auth stress 400 41.110 290,9 2 3 4 0,00 %
    replicas-2 auth stress 400 40.810 287,1 2 17 114 0,00 %
    replicas-4 auth stress 400 40.918 285,8 3 7 23 0,00 %
    exchange-cache-off exchange load 10 445 7,3 23 49 69 0,00 %
    exchange-cache-on exchange load 10 454 7,5 3 4 17 0,00 %
    mixed-load mixed load 50 6.605 72,1 4 62 197 0,00 %
    saturation-1 auth stress, THINK=0 200 578.564 4.120 13 43 69 0,57 %
    saturation-4 auth stress, THINK=0 200 387.296 2.697 14 88 166 0,00 %

    Todos os cenários com pausa (1–4) ficaram dentro do SLO (erros < 1 %, p95 < 500 ms, p99 < 1,5 s).

    O que os números mostram

    1. Cache do token (Redis) — o Auth sai do caminho. Com o cache ligado, o Prometheus registrou 7.571 hits e 21 misses em gateway_token_cache_total durante a rodada: 99,7 % das validações não chamaram o Auth (os 21 misses são ≈ 1 por usuário do teste). Sem cache, todas as ≈ 7.400 requisições passaram pelo POST /auth/solve. A latência caiu de p95 12 → 7 ms (−42 %). A vazão é a mesma nas duas rodadas porque quem dita o ritmo é a pausa dos usuários, não o servidor.

    2. Cache da cotação — a API externa sai do caminho. Sem cache, toda cotação ia até a AwesomeAPI: p50 de 23 ms e p95 de 49 ms, a latência de um serviço de terceiros. Com o cache de 30 s, p50 de 3 ms e p95 de 4 ms (−92 %). Em 10 usuários a API externa aguentou sem 429, mas o volume de chamadas a ela cai de ≈ 7 por segundo para 1 a cada 30 s por réplica — é isso que protege do limite de requisições.

    3. Réplicas com carga "realista" — um gateway sobra. Com a pausa entre ações, 400 usuários geram ≈ 290 req/s, e uma réplica só responde com p95 de 3 ms. As diferenças entre 1, 2 e 4 réplicas (3 / 17 / 7 ms) são ruído de JVMs recém-criadas (ainda sem o JIT aquecido), não ganho nem perda. Conclusão honesta: nessa carga o gateway não é o gargalo; o motivo para ter 2+ réplicas é disponibilidade (uma pode cair), não capacidade.

    4. Saturação — achamos o gargalo real, e não era o gateway. Sem pausa, a plataforma passou de 4.100 req/s com uma réplica do gateway, mas 0,57 % das requisições falharam (3.279), todas em GET /auth/me, nenhuma em GET /accounts/{id}. O gateway devolveu 500 e o log do Auth mostrou exatamente 3.279 × java.net.BindException: Cannot assign requested address:

    flowchart LR
    gw[gateway] -->|"GET /auth/me"| auth[Auth]
    auth -->|"Feign: 1 conexão TCP nova<br/>por chamada (sem pool)"| acc[Account]
    auth -.-x|"portas efêmeras<br/>esgotadas → 500"| acc

    O GET /auth/me do Auth chama o Account pelo OpenFeign com o cliente HTTP padrão, sem pool de conexões: cada requisição abre uma conexão TCP nova, e a 4.000 req/s as portas locais do container do Auth acabam (as fechadas ficam em TIME_WAIT). Com 4 réplicas do gateway a máquina ficou mais ocupada (CPU em ≈ 83 % nas duas rodadas, 4 JVMs disputando os mesmos núcleos), a vazão caiu para 2.697 req/s e o Auth não chegou no limite — por isso 0 erros, mas p95 o dobro.

    Correção sugerida (Auth — Nicolas)

    Trocar o cliente do Feign por um com pool de conexões e keep-alive — adicionar io.github.openfeign:feign-hc5 ao auth-service e spring.cloud.openfeign.httpclient.hc5.enabled=true. Com conexões reaproveitadas, o Auth deixa de abrir uma porta por requisição. Depois, repetir ONLY=5 ./scripts/load-matrix.sh para confirmar que os 500 somem.

    5. Uso real (mixed). Dentro do SLO, mas com a cauda mais longa da bateria (p95 62 ms, p99 197 ms): 5 % das ações são POST /auth/login, que faz o hash da senha (custoso de propósito) e emite o JWT.

    Limitações

    • Tudo na mesma máquina: o k6 disputa CPU com a plataforma. Os números mostram tendências e gargalos, não a capacidade do EKS. Em nós separados, mais réplicas devem aumentar a vazão — aqui ficaram presas à mesma CPU.
    • Rodadas curtas (1–3 min) e uma execução por configuração: diferenças de poucos ms são ruído.
    • 20 contas reutilizadas: favorece o cache do token (é o padrão de uso logado, mas um teste com milhares de usuários novos teria mais misses).

    Para medir a capacidade real: BASE_URL=http://<elb> ./scripts/load-test.sh a partir de outra máquina.

    Teste no EKS com HPA

    O curso pede um vídeo do teste de carga em execução com o HPA escalando. Roteiro para o dia do EKS: k6 rodando da máquina de um integrante contra o ELB, e o Horizontal Pod Autoscaler criando réplicas do gateway quando a CPU média passa de 50 % do request (250m → 125m por pod).

    Antes de começar

    • metrics-server instalado no cluster (o EKS não traz; sem ele o HPA fica em <unknown>).
    • Cenário auth (ou mixed), não exchange: a AwesomeAPI devolveu 429 para o IP da AWS, então o Exchange responde 503 no EKS.
    • Ninguém faz push na main durante a gravação: o deploy do CI faz kubectl apply do manifesto do gateway (replicas: 2) e briga com o HPA.
    • Capacidade: os 2 nós fixos têm espaço para mais ≈ 6 réplicas do gateway (conta em Custos). Com --max=10, as réplicas 9 e 10 ficariam Pending. Por isso o roteiro usa --max=6; se o grupo preferir mostrar o limite, --max=10 e os Pending viram parte do resultado.

    Três terminais lado a lado (no Windows não existe watch; o -w do kubectl faz o mesmo):

    kubectl autoscale deployment gateway --cpu-percent=50 --min=2 --max=6 -n store
kubectl get hpa gateway -n store -w

    kubectl get pods -n store -l app=gateway -o wide -w

    ELB=$(kubectl get svc lb -n store -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
# (opcional) métricas do k6 no Grafana do cluster: noutro terminal,
#   kubectl port-forward svc/prometheus 9090 -n store
BASE_URL=http://$ELB PROMETHEUS_RW_URL=http://host.docker.internal:9090 \
  NAME=eks-hpa SCENARIO=auth PROFILE=load VUS=100 DURATION=4m THINK=0 ./scripts/load-test.sh

    --min=2 porque o manifesto do gateway já sobe 2 réplicas: com --min=1 o HPA derrubaria uma logo no começo do vídeo. O HPA olha a CPU a cada 15 s e o metrics-server tem até ≈ 1 min de atraso, por isso o platô tem 4 min. Depois do teste, o HPA espera 5 min sem carga antes de reduzir as réplicas: dá para continuar gravando e mostrar a volta para 2.

    Print do Grafana durante o teste (página de Observabilidade): kubectl port-forward svc/grafana 3000 -n store, dashboard Store — plataforma. Os painéis "Requisições/s por réplica" e "CPU por réplica" mostram as réplicas novas entrando e dividindo a carga.

    Depois: apagar o HPA (kubectl delete hpa gateway -n store) antes de apagar o cluster.

    // Teste de carga da plataforma (k6). Rodar com ./scripts/load-test.sh.
//
// Variáveis:
//   BASE_URL  http://lb (dentro da rede do compose) ou o endereço do ELB
//   SCENARIO  auth | exchange | login | mixed           (padrão: mixed)
//   PROFILE   smoke | load | stress | spike              (padrão: load)
//   VUS       usuários virtuais no platô                 (padrão: 50)
//   DURATION  duração do platô                           (padrão: 1m)
//   USERS     contas criadas no setup e reutilizadas     (padrão: 20)
//   NAME      nome do resultado em load/results/          (padrão: SCENARIO-PROFILE)
//   THINK     pausa entre ações, em s (padrão: 0.5-1.5 aleatório; 0 = sem pausa,
//             para achar o limite de vazão)
//
// Cenários:
//   auth      GET /auth/me + GET /accounts/{id}: rota protegida -> gateway valida o
//             token (Redis ou Auth) -> serviço. Mede cache do token e balanceamento.
//   exchange  GET /exchange/USD/BRL (e EUR/BRL): mede o cache da cotação.
//   login     POST /auth/login: caminho caro (hash da senha + emissão do JWT).
//   mixed     80% leitura autenticada, 15% câmbio, 5% login (uso "real" da loja).

import http from 'k6/http';
import { check, sleep } from 'k6';
import exec from 'k6/execution';
import { textSummary } from 'https://jslib.k6.io/k6-summary/0.1.0/index.js';

const BASE_URL = __ENV.BASE_URL || 'http://lb';
const SCENARIO = __ENV.SCENARIO || 'mixed';
const PROFILE = __ENV.PROFILE || 'load';
const VUS = parseInt(__ENV.VUS || '50', 10);
const DURATION = __ENV.DURATION || '1m';
const USERS = parseInt(__ENV.USERS || '20', 10);
const NAME = __ENV.NAME || `${SCENARIO}-${PROFILE}`;
const THINK = __ENV.THINK;
const PASSWORD = 'carga-senha-123';

const PROFILES = {
  // 1 usuário, só para ver se o script e a plataforma funcionam
  smoke: [
    { duration: '1s', target: 1 },
    { duration: '20s', target: 1 },
  ],
  // carga esperada: sobe, mantém o platô, desce
  load: [
    { duration: '20s', target: VUS },
    { duration: DURATION, target: VUS },
    { duration: '10s', target: 0 },
  ],
  // aumenta até achar o ponto de quebra (onde p95 ou erros estouram)
  stress: [
    { duration: '30s', target: VUS },
    { duration: '30s', target: VUS * 2 },
    { duration: '30s', target: VUS * 4 },
    { duration: '30s', target: VUS * 8 },
    { duration: '20s', target: 0 },
  ],
  // pico repentino (ex.: promoção): a plataforma se recupera?
  spike: [
    { duration: '10s', target: Math.max(1, Math.floor(VUS / 10)) },
    { duration: '5s', target: VUS * 4 },
    { duration: '30s', target: VUS * 4 },
    { duration: '5s', target: Math.max(1, Math.floor(VUS / 10)) },
    { duration: '30s', target: Math.max(1, Math.floor(VUS / 10)) },
    { duration: '5s', target: 0 },
  ],
};

export const options = {
  scenarios: {
    [SCENARIO]: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: PROFILES[PROFILE] || PROFILES.load,
      gracefulRampDown: '10s',
    },
  },
  // SLO do projeto (ver docs/devops/custos-sla.md): o k6 sai com código 99 se estourar.
  // Só conta a fase de teste (phase:test): o cadastro/login do setup() fica de fora.
  thresholds: {
    'http_req_failed{phase:test}': ['rate<0.01'],
    'http_req_duration{phase:test,expected_response:true}': ['p(95)<500', 'p(99)<1500'],
    'http_reqs{phase:test}': ['count>0'],
    checks: ['rate>0.99'],
  },
  summaryTrendStats: ['avg', 'med', 'p(90)', 'p(95)', 'p(99)', 'max'],
  setupTimeout: '2m',
  tags: { testid: NAME },
};

const JSON_HEADERS = { 'Content-Type': 'application/json' };

// tag "phase": separa o setup() (cadastro/login das contas) da carga medida
const tags = (name, phase = 'test') => ({ name, phase });

function login(email, phase = 'test') {
  const res = http.post(`${BASE_URL}/auth/login`, JSON.stringify({ email, password: PASSWORD }), {
    headers: JSON_HEADERS,
    tags: tags('POST /auth/login', phase),
  });
  const cookie = res.cookies.__store_jwt_token;
  return cookie && cookie.length ? cookie[0].value : null;
}

// Cria USERS contas e faz login uma vez: os VUs reutilizam os tokens, como
// usuários reais navegando logados (é isso que o cache do token aproveita).
export function setup() {
  const run = `${Date.now()}`;
  const users = [];
  for (let i = 0; i < USERS; i++) {
    const email = `carga+${run}-${i}@store.test`;
    const reg = http.post(
      `${BASE_URL}/auth/register`,
      JSON.stringify({ name: `Carga ${i}`, email, password: PASSWORD }),
      { headers: JSON_HEADERS, tags: tags('setup', 'setup') },
    );
    if (reg.status !== 200 && reg.status !== 201) {
      exec.test.abort(`POST /auth/register respondeu ${reg.status}: ${reg.body}`);
    }
    const token = login(email, 'setup');
    if (!token) exec.test.abort('login não devolveu o cookie __store_jwt_token');
    const me = http.get(`${BASE_URL}/auth/me`, {
      headers: { Cookie: `__store_jwt_token=${token}` },
      tags: tags('setup', 'setup'),
    });
    users.push({ email, token, id: me.json('id') });
  }
  return { users };
}

function authRead(user) {
  const params = { headers: { Cookie: `__store_jwt_token=${user.token}` } };
  const me = http.get(`${BASE_URL}/auth/me`, Object.assign({ tags: tags('GET /auth/me') }, params));
  check(me, { 'auth/me 200': (r) => r.status === 200 });
  const acc = http.get(`${BASE_URL}/accounts/${user.id}`, Object.assign({ tags: tags('GET /accounts/{id}') }, params));
  check(acc, { 'accounts/{id} 200': (r) => r.status === 200 });
}

function exchange(user) {
  const pair = Math.random() < 0.8 ? 'USD/BRL' : 'EUR/BRL';
  const res = http.get(`${BASE_URL}/exchange/${pair}`, {
    headers: { Cookie: `__store_jwt_token=${user.token}` },
    tags: tags('GET /exchange/{from}/{to}'),
  });
  check(res, {
    'exchange 200': (r) => r.status === 200,
    'exchange sell >= buy': (r) => r.status === 200 && r.json('sell') >= r.json('buy'),
  });
}

function doLogin(user) {
  check(login(user.email), { 'login devolve token': (t) => !!t });
}

export default function (data) {
  const user = data.users[(exec.vu.idInTest - 1) % data.users.length];
  switch (SCENARIO) {
    case 'auth':
      authRead(user);
      break;
    case 'exchange':
      exchange(user);
      break;
    case 'login':
      doLogin(user);
      break;
    default: {
      const r = Math.random();
      if (r < 0.8) authRead(user);
      else if (r < 0.95) exchange(user);
      else doLogin(user);
    }
  }
  // "tempo de leitura" do usuário: sem isso cada VU vira um loop sem pausa
  if (THINK === undefined) sleep(0.5 + Math.random());
  else if (parseFloat(THINK) > 0) sleep(parseFloat(THINK));
}

// Resumo no terminal + JSON completo + uma linha de tabela markdown, para o
// scripts/load-matrix.sh juntar os resultados em load/results/RESULTS.md.
export function handleSummary(data) {
  const m = data.metrics;
  // só a fase de teste (submétricas criadas pelos thresholds com {phase:test})
  const d = m['http_req_duration{phase:test,expected_response:true}'];
  const reqs = m['http_reqs{phase:test}'];
  const failed = m['http_req_failed{phase:test}'];
  const fmt = (v) => (v === undefined ? '-' : v.toFixed(0));
  const row =
    `| ${NAME} | ${SCENARIO} | ${PROFILE} | ${m.vus_max ? m.vus_max.values.max : '-'} ` +
    `| ${reqs.values.count} | ${reqs.values.rate.toFixed(1)} ` +
    `| ${fmt(d.values.med)} | ${fmt(d.values['p(95)'])} | ${fmt(d.values['p(99)'])} ` +
    `| ${(failed.values.rate * 100).toFixed(2)} % |\n`;
  return {
    stdout: textSummary(data, { indent: ' ', enableColors: true }),
    [`/results/${NAME}.json`]: JSON.stringify(data, null, 2),
    [`/results/${NAME}.row.md`]: row,
  };
}

    #!/usr/bin/env bash
# Roda um teste de carga (k6, via Docker) contra a plataforma.
#
#   ./scripts/load-test.sh                               # cenário mixed, perfil load, 50 VUs
#   SCENARIO=auth PROFILE=stress VUS=50 ./scripts/load-test.sh
#   BASE_URL=http://<elb-da-aws> ./scripts/load-test.sh  # contra o EKS
#   BASE_URL=http://<elb> PROMETHEUS_RW_URL=http://host.docker.internal:9090 ./scripts/load-test.sh
#                                                        # EKS + métricas no Prometheus do cluster
#
# Sem BASE_URL, o k6 entra na rede do compose e chama o lb por dentro (http://lb),
# e manda as métricas para o Prometheus do compose (aparecem no Grafana, linha
# "Teste de carga (k6)"). Resultados em load/results/<NAME>.json e .row.md.
# Variáveis aceitas: ver o cabeçalho de load/store.js.
set -euo pipefail

ROOT="$(cd "$(dirname "$0")/.." && pwd)"
cd "$ROOT"

K6_IMAGE="grafana/k6:1.3.0"
SCENARIO="${SCENARIO:-mixed}"
PROFILE="${PROFILE:-load}"
NAME="${NAME:-$SCENARIO-$PROFILE}"
mkdir -p load/results
# o container do k6 roda como usuário sem privilégio: precisa poder gravar o resultado
chmod a+w load/results 2>/dev/null || true

ARGS=(run --rm -i
  -v "$ROOT/load:/scripts:ro"
  -v "$ROOT/load/results:/results"
  -e SCENARIO="$SCENARIO" -e PROFILE="$PROFILE" -e NAME="$NAME"
  -e VUS="${VUS:-50}" -e DURATION="${DURATION:-1m}" -e USERS="${USERS:-20}")
[ -n "${THINK:-}" ] && ARGS+=(-e THINK="$THINK")
K6_ARGS=(run)

if [ -z "${BASE_URL:-}" ]; then
  NETWORK="$(docker compose ps -q lb | xargs -r docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}}{{end}}' 2>/dev/null || true)"
  [ -n "$NETWORK" ] || { echo "a plataforma não está no ar: docker compose up -d --build" >&2; exit 1; }
  ARGS+=(--network "$NETWORK" -e BASE_URL=http://lb)
  if [ -n "$(docker compose ps -q prometheus 2>/dev/null)" ]; then
    ARGS+=(-e K6_PROMETHEUS_RW_SERVER_URL=http://prometheus:9090/api/v1/write
           -e "K6_PROMETHEUS_RW_TREND_STATS=p(95),p(99),avg,max"
           -e K6_PROMETHEUS_RW_PUSH_INTERVAL=5s)
    K6_ARGS+=(-o experimental-prometheus-rw)
  fi
  TARGET="http://lb (rede $NETWORK)"
else
  ARGS+=(-e BASE_URL="$BASE_URL")
  TARGET="$BASE_URL"
  # EKS: com "kubectl port-forward svc/prometheus 9090 -n store" aberto, as métricas
  # do k6 vão para o Prometheus do cluster (o container chega no host por
  # host.docker.internal):  PROMETHEUS_RW_URL=http://host.docker.internal:9090
  if [ -n "${PROMETHEUS_RW_URL:-}" ]; then
    ARGS+=(--add-host=host.docker.internal:host-gateway
           -e K6_PROMETHEUS_RW_SERVER_URL="${PROMETHEUS_RW_URL%/}/api/v1/write"
           -e "K6_PROMETHEUS_RW_TREND_STATS=p(95),p(99),avg,max"
           -e K6_PROMETHEUS_RW_PUSH_INTERVAL=5s)
    K6_ARGS+=(-o experimental-prometheus-rw)
  fi
fi

echo ">> k6: cenário=$SCENARIO perfil=$PROFILE VUs=${VUS:-50} alvo=$TARGET"
# MSYS_NO_PATHCONV: no Git Bash (Windows) evita converter /scripts em C:/Program Files/Git/scripts
MSYS_NO_PATHCONV=1 docker "${ARGS[@]}" "$K6_IMAGE" "${K6_ARGS[@]}" /scripts/store.js

    #!/usr/bin/env bash
# Roda a bateria de testes de carga da documentação (docs/devops/load-testing.md)
# e junta tudo em load/results/RESULTS.md. Leva ~20 min. Pré-requisito:
#   ./scripts/build.sh && docker compose up -d --build
#
# Cada experimento muda UMA variável e mantém o resto igual:
#   1. cache do token     TOKEN_CACHE_ENABLED=true x false   (cenário auth)
#   2. réplicas           GATEWAY_REPLICAS=1 x 2 x 4         (cenário auth, perfil stress)
#   3. cache da cotação   EXCHANGE_CACHE_TTL=30 x 0          (cenário exchange, poucos VUs:
#                         sem cache cada requisição vai para a API externa e não queremos
#                         martelar um serviço de terceiros)
#   4. uso real           mixed, perfil load, configuração padrão
#   5. saturação          GATEWAY_REPLICAS=1 x 4 com THINK=0 (usuários sem pausa): acha o
#                         limite de vazão, que o experimento 2 (com pausa) não alcança
#
#   ONLY="1 3" ./scripts/load-matrix.sh     # roda só alguns experimentos
set -uo pipefail

ROOT="$(cd "$(dirname "$0")/.." && pwd)"
cd "$ROOT"
OUT=load/results/RESULTS.md
ONLY="${ONLY:-1 2 3 4 5}"
VUS="${VUS:-50}"

want() { [[ " $ONLY " == *" $1 "* ]]; }

# sobe a plataforma com a configuração do experimento e espera ficar saudável
configure() {
  echo ">> configurando: $*"
  env "$@" docker compose up -d --wait --wait-timeout 300 gateway exchange >/dev/null
  # cache do token frio em todo experimento (é só cache, pode apagar)
  docker compose exec -T redis redis-cli FLUSHDB >/dev/null
  # o gateway (Spring) leva alguns segundos para subir depois do "running"
  for _ in $(seq 1 60); do
    curl -sf -o /dev/null "http://localhost:${LB_PORT:-8080}/health-check" && break
    sleep 2
  done
  # o Nginx re-resolve o DNS das réplicas a cada 10 s
  sleep 12
}

run() { # run NAME SCENARIO PROFILE VUS [DURATION] [THINK]
  NAME="$1" SCENARIO="$2" PROFILE="$3" VUS="$4" DURATION="${5:-1m}" THINK="${6:-}" ./scripts/load-test.sh || \
    echo "aviso - $1 estourou algum threshold (ver o resumo acima)"
}

row() { cat "load/results/$1.row.md" 2>/dev/null || echo "| $1 | (falhou) |"; }

DEFAULTS=(TOKEN_CACHE_ENABLED=true GATEWAY_REPLICAS=2 EXCHANGE_CACHE_TTL=30)

if want 1; then
  configure "${DEFAULTS[@]/TOKEN_CACHE_ENABLED=true/TOKEN_CACHE_ENABLED=false}"
  run token-cache-off auth load "$VUS"
  configure "${DEFAULTS[@]}"
  run token-cache-on auth load "$VUS"
fi

if want 2; then
  for n in 1 2 4; do
    configure TOKEN_CACHE_ENABLED=true GATEWAY_REPLICAS=$n EXCHANGE_CACHE_TTL=30
    run "replicas-$n" auth stress "$VUS"
  done
fi

if want 3; then
  configure "${DEFAULTS[@]/EXCHANGE_CACHE_TTL=30/EXCHANGE_CACHE_TTL=0}"
  run exchange-cache-off exchange load 10 30s
  configure "${DEFAULTS[@]}"
  run exchange-cache-on exchange load 10 30s
fi

if want 4; then
  configure "${DEFAULTS[@]}"
  run mixed-load mixed load "$VUS"
fi

if want 5; then
  for n in 1 4; do
    configure TOKEN_CACHE_ENABLED=true GATEWAY_REPLICAS=$n EXCHANGE_CACHE_TTL=30
    run "saturation-$n" auth stress 25 1m 0
  done
fi

# volta para a configuração padrão
configure "${DEFAULTS[@]}"

{
  echo "# Resultados do teste de carga"
  echo
  echo "- Data: $(date '+%Y-%m-%d %H:%M')"
  echo "- Máquina: $(docker info --format '{{.OperatingSystem}}, {{.NCPU}} CPUs, {{.MemTotal}} bytes de RAM para o Docker' 2>/dev/null)"
  echo "- k6, Nginx, gateway e serviços na **mesma máquina** (o k6 disputa CPU com a plataforma)"
  echo
  echo "Latências em ms, só respostas esperadas (2xx/3xx). Erros = % de respostas 4xx/5xx/timeout."
  echo
  echo "| Execução | Cenário | Perfil | VUs máx. | Requisições | req/s | p50 | p95 | p99 | Erros |"
  echo "|---|---|---|---:|---:|---:|---:|---:|---:|---:|"
  for n in token-cache-off token-cache-on replicas-1 replicas-2 replicas-4 exchange-cache-off exchange-cache-on mixed-load saturation-1 saturation-4; do
    [ -f "load/results/$n.row.md" ] && row "$n"
  done
} > "$OUT"

echo ">> tabela em $OUT"
cat "$OUT"
